# Outbox/Inbox 模式如何保证可靠投递和消费

## 整体链路

```
生产方服务                          消费方服务
┌─────────────────┐               ┌─────────────────┐
│ 业务库           │               │ 业务库           │
│  ├─ 业务表       │               │  ├─ 业务表       │
│  └─ outbox 表    │──→ MQ ──→    │  └─ inbox 表     │
└─────────────────┘               └─────────────────┘
```

可靠性由三段共同保证：

| 环节   | 目标                             | 机制                   |
| :----- | :------------------------------- | :--------------------- |
| 生产端 | 业务成功则消息一定发出           | Outbox 模式 + 本地事务 |
| 传输端 | 消息不丢                         | MQ 持久化 + ACK 机制   |
| 消费端 | 消息收到则一定处理，且只处理一次 | Inbox 模式 + 幂等消费  |

## 生产端：Outbox 模式

**要解决的问题**：业务写库和发消息是两个操作，不在同一事务里，可能不一致。

**做法**：

1. 在同一个本地事务中，同时完成：
   - 更新业务表；
   - 向 Outbox 表插入一条 `status = PENDING` 的记录。
2. 事务提交后，由后台进程（轮询或 CDC）从 Outbox 表读取待发送记录，投递到 MQ。
3. 投递成功后，更新 `status = SENT`。

**保证**：

- 业务成功 → Outbox 记录一定存在 → 消息最终一定被投递。
- 业务失败 → 事务回滚 → 消息不会发出。
- 投递失败可重试，不会丢消息。

**关键设计**：

- Outbox 表与业务表同库，共享本地事务。
- Outbox 记录的 `id` 作为 `message_id` 和 `event_type` 一并传给下游，用于消息去重。
- 投递语义是**至少一次（at-least-once）**，可能重复，所以消费端必须幂等。

## 传输端：MQ 的可靠性

**要解决的问题**：消息在 broker 里不能丢。

**做法**：

- **持久化**：消息写入磁盘，broker 重启不丢。
- **副本**：Kafka 多副本、RabbitMQ 镜像队列，防止单点故障。
- **ACK 机制**：生产方等待 broker 确认写入成功，才算投递完成。
- **重试**：投递失败时重试，配合 Outbox 表的 `retry_count` 和 `last_error`。

**保证**：消息一旦进入 MQ，就不会因为 broker 故障而丢失。

**注意**：传输端仍然可能重复投递（如 ACK 丢失导致重发），所以整体语义仍是**至少一次**。

## 消费端：Inbox 模式

**要解决的问题**：消息可能重复投递，业务处理必须幂等。

**做法**：

1. 消费者收到消息后，**不直接执行业务逻辑**，而是先尝试向 Inbox 表插入记录。
2. Inbox 表的 `event_type`、`message_id` 上有组合唯一索引：
   - 插入成功 → 第一次收到，继续处理；
   - 插入冲突 → 已处理过，直接 ACK 跳过。
3. 插入成功后，在同一本地事务中执行业务逻辑（更新消费方业务表）。
4. 处理成功后标记 `status = 已完成`；失败则重试。
5. 向 MQ 发送 ACK，表示消息已可靠接收。

**保证**：

- 重复消息被唯一索引拦截，业务只执行一次。
- 消息先落库再处理，即使处理失败也能从 Inbox 表重试。
- 接收与处理解耦，接收阶段只做可靠落库。

**关键设计**：

- Inbox 表与消费方业务表同库，保证“去重 + 业务处理”在同一事务。
- `message_id` 由生产方保证全局唯一，或使用 `(event_type, message_id)` 组合唯一。
- 一个服务消费多个 topic，仍只需一张 Inbox 表。

## 五、端到端语义

| 环节          | 语义                     |
| ------------- | ------------------------ |
| 生产端 Outbox | 至少一次投递             |
| 传输端 MQ     | 至少一次投递             |
| 消费端 Inbox  | 幂等消费，效果上恰好一次 |

**组合结果**：

至少一次投递 + 幂等消费 = 效果上的恰好一次处理（effectively exactly-once）

这是分布式系统中在不依赖分布式事务的前提下，实现可靠消息传递的标准方案。

## 关键设计点速查

| 问题                           | 答案                                               |
| ------------------------------ | -------------------------------------------------- |
| Outbox 表放哪                  | 生产方业务库，与业务表同事务                       |
| Inbox 表放哪                   | 消费方业务库，与业务表同事务                       |
| message_id 怎么来              | Outbox 记录的 id/message_id，全局唯一              |
| 如何保证不丢                   | Outbox 本地事务 + MQ 持久化 + Inbox 先落库         |
| 如何保证不重                   | Inbox 表 message_id 唯一索引                       |
| 消费多个 topic 要几张 Inbox 表 | 一张，加 topic 字段记录来源                        |
| 消息顺序怎么保证               | 按 aggregate_id 分区，同一聚合进同一分区           |
| 失败怎么办                     | Outbox/Inbox 表记录重试次数和错误，超过阈值转死信  |
| 表会无限增长怎么办             | 定期归档或删除已完成记录，保留时间覆盖最大重投延迟 |

## 总结

Outbox 保证“业务成功则消息一定发出”，MQ 保证“消息在传输中不丢”，Inbox 保证“消息收到则一定处理且只处理一次”。三者结合，用至少一次投递加幂等消费，实现效果上的恰好一次处理。
